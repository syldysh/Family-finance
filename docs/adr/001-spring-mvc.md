# Почему Spring MVC, а не WebFlux

## Суть

Spring предлагает два подхода: Spring MVC (классический, блокирующий) и Spring WebFlux (реактивный, неблокирующий). Мне нужно было выбрать один из них для REST API.

## Что я выбрала и почему

Я выбрала Spring MVC по нескольким причинам.

Во-первых, проект использует Spring Data JPA с Hibernate — это блокирующий API. Чтобы использовать WebFlux, пришлось бы перейти на R2DBC (реактивный драйвер для БД), а это значит потерять все плюсы ORM: ленивую загрузку, каскады, кэш первого уровня. Переписывать весь слой доступа к данным ради реактивности не имеет смысла.

Во-вторых, Thymeleaf, который я использую для UI, работает только с MVC. С WebFlux пришлось бы переделывать фронтенд.

В-третьих, само приложение — CRUD с небольшим количеством одновременных пользователей. WebFlux даёт ощутимый выигрыш при тысячах одновременных соединений и неблокирующих источниках данных. Здесь такого нет.

Ну и наконец, стек вызовов в MVC линейный и читаемый — отладка значительно проще, чем работа с Mono/Flux в реактивном стеке.

## Итог

Spring MVC полностью совместим с JPA и Thymeleaf, прост в отладке и достаточен для текущих задач. Если в перспективе нагрузка вырастет, можно масштабировать горизонтально, а не переписывать на WebFlux.
