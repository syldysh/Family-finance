# Почему Spring Data JPA

## Суть

Для доступа к данным в Spring есть несколько вариантов: Spring Data JPA (Hibernate), Spring Data JDBC (без ORM), MyBatis, чистый JdbcTemplate. Можно было и вовсе уйти от реляционной модели — например, взять MongoDB.

## Что я выбрала и почему

Я остановилась на Spring Data JPA с Hibernate.

Доменная модель в проекте достаточно связная: User → Family → FamilyMember → Transaction → Category. JPA позволяет описать все эти связи через аннотации (`@ManyToOne`, `@OneToMany`), управлять загрузкой через `FetchType.LAZY` и использовать каскады. Это удобнее, чем вручную писать JOIN-запросы.

Для сложных выборок (фильтрация транзакций по дате, типу, категории, пользователю) я использую кастомные `@Query` с JPQL — запросы к объектной модели, а не к таблицам напрямую.

Управление транзакциями — через `@Transactional` и `@Transactional(readOnly = true)`. Для финансового приложения это критично: нужны чёткие границы транзакций.

Для борьбы с N+1 я использовала batch-загрузку (`findAllByFamilyIds`) — один запрос на все связанные сущности вместо отдельного на каждую.

Spring Data JDBC был бы проще, но он не поддерживает ленивую загрузку и кэш первого уровня — при такой модели со связями это привело бы к лишним запросам. MongoDB не подходит, потому что финансовые данные по природе реляционные — агрегация по категориям, отчёты, контроль целостности через foreign keys.

## Итог

JPA хорошо подходит для сложной реляционной модели с кастомными запросами и транзакционным контролем. В перспективе можно добавить кэш второго уровня или перейти на batch-операции для тяжёлых отчётов.
