# Почему отдельные базы данных для сервисов

## Суть

В микросервисной архитектуре нужно решить, как сервисы хранят данные: одна общая БД на все сервисы или у каждого своя.

## Что я выбрала и почему

Я реализовала паттерн Database-per-Service: auth-service работает с `auth_db`, finance-service — с `finance_db`. Report-service вообще без собственной базы — он получает данные через REST API из finance-service.

Главная причина — изоляция. auth-service не имеет прямого доступа к таблицам finance-service, и наоборот. Это исключает случайные зависимости на уровне БД: общие таблицы, неявные JOIN-ы, привязку к чужой схеме.

Каждый сервис можно обновить и мигрировать независимо — миграция схемы auth_db не затрагивает finance-service. Если завтра я захочу поменять структуру таблицы users, finance-service этого даже не заметит, пока REST-контракт остаётся прежним.

Report-service я сделала stateless — он строит отчёт на лету из транзакций, полученных по API. Ему не нужна своя база, и это упрощает его деплой.

В Docker Compose каждая БД — отдельный контейнер (`postgres-auth`, `postgres-finance`) со своим volume.

Из компромиссов: раз нельзя делать JOIN между базами, email пользователя дублируется в таблице `family_member` — денормализация, зато для отображения списка участников не нужно каждый раз обращаться к auth-service.

## Итог

Отдельные базы обеспечивают слабую связанность сервисов и возможность независимого развёртывания. В перспективе это позволит, например, вынести auth-service на отдельный сервер без изменения кода finance-service.
