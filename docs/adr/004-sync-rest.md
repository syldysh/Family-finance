# Почему синхронный REST между сервисами

## Суть

Между микросервисами нужна коммуникация. Варианты: синхронный REST, асинхронные очереди (Kafka, RabbitMQ), gRPC.

## Что я выбрала и почему

Я выбрала синхронный REST через `RestClient` (Spring 6.1).

Все сценарии взаимодействия в проекте — это запрос-ответ, где пользователь ждёт результат прямо сейчас:
- Добавление участника в семью — finance-service ищет пользователя по email в auth-service и сразу возвращает результат
- Построение отчёта — report-service запрашивает транзакции из finance-service, пользователь ждёт отчёт на экране
- Проксирование отчётов — finance-service передаёт запрос в report-service и возвращает ответ в UI

Для таких сценариев асинхронные очереди вроде Kafka или RabbitMQ избыточны — они хороши для событийной модели (fire-and-forget), когда отправителю не нужен ответ. Здесь же ответ нужен немедленно.

К тому же, очереди потребовали бы разворачивать и обслуживать дополнительную инфраструктуру. Для проекта с тремя сервисами это неоправданная сложность.

`RestClient` я выбрала вместо устаревшего `RestTemplate` — это современный API с fluent-интерфейсом, появившийся в Spring 6.1.

Слабое место синхронного подхода — временная связанность: если auth-service упал, finance-service не сможет добавить участника. Эту проблему я смягчила с помощью Retry (Resilience4j).

## Итог

Синхронный REST — простой и предсказуемый выбор для сценариев запрос-ответ. В перспективе, если появятся фоновые задачи (например, рассылка уведомлений по email), можно будет добавить очередь для них отдельно.
