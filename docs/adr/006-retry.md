# Почему Retry для отказоустойчивости

## Суть

Синхронные HTTP-вызовы между сервисами уязвимы к кратковременным сбоям: сеть моргнула, сервис перезагружается, временная перегрузка. Нужно было выбрать паттерн для повышения надёжности. Рассматривала Retry, Circuit Breaker, Cache и Rate Limiter.

## Что я выбрала и почему

Я внедрила Retry через Resilience4j.

Retry — самый простой и подходящий паттерн для моего сценария. Кратковременный сбой (сервис перезагружается, сеть на секунду пропала) — именно то, что решается повторным вызовом. Повторить запрос через 500ms — и с большой вероятностью он пройдёт.

Конфигурация:
- **3 попытки** (включая первую)
- **500ms** пауза между попытками
- Повтор только при `ServiceUnavailableException` — бизнес-ошибки (`NotFoundException`, `AccessDeniedException`) не повторяются, потому что повторный запрос ничего не изменит

Внедрение минимальное: аннотация `@Retry(name = "...")` на методе клиента + конфигурация в `application.yml`. Код самих клиентов не меняется.

Где применила:
- `AuthServiceClient.getUserByEmail()` — finance-service → auth-service
- Все три метода `FinanceServiceClient` — report-service → finance-service

Circuit Breaker я не стала добавлять — он полезен при длительных отказах (минуты), чтобы не нагружать упавший сервис. Для проекта с тремя сервисами на одной машине Retry вполне достаточно. В перспективе, если добавить Circuit Breaker, Resilience4j позволяет комбинировать его с Retry без переписывания кода.

## Итог

Retry прозрачно обрабатывает кратковременные сбои. Максимальное время ожидания при полном отказе — около 1.5 секунд, после чего пользователь получит понятную ошибку «Сервис недоступен».
