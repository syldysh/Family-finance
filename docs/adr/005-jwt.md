# Почему JWT для аутентификации

## Суть

Нужно было выбрать механизм аутентификации для микросервисной системы: серверные сессии (stateful), JWT (stateless) или OAuth2 с Authorization Server.

## Что я выбрала и почему

Я выбрала JWT с библиотекой JJWT 0.12.5.

Главное преимущество JWT в микросервисной архитектуре — stateless. Сервисам не нужно обращаться к auth-service для проверки каждого запроса — токен валидируется локально. Это упрощает масштабирование: любой экземпляр любого сервиса может проверить токен самостоятельно.

Общий секретный ключ я вынесла в common-модуль (`JwtProperties`), а `JwtAuthenticationFilter` реализовала там же — он подключается во все сервисы через `@ComponentScan`.

Для защиты внутреннего API (когда report-service обращается к finance-service за транзакциями) я сделала отдельный механизм — `InternalTokenFilter` с фиксированным токеном в заголовке `X-Internal-Token`. Передавать пользовательский JWT между сервисами не хотелось — это лишняя связанность.

Серверные сессии не подошли бы — они требуют общего хранилища (Redis или БД), чтобы все экземпляры сервисов видели одни и те же сессии. JWT избавляет от этой зависимости.

OAuth2 с отдельным Authorization Server — слишком тяжёлый вариант для проекта с одним провайдером аутентификации. Он оправдан при интеграции с внешними системами, здесь этого нет.

## Итог

JWT обеспечивает простую stateless-аутентификацию через общий модуль. Из минусов — нельзя отозвать отдельный токен до истечения его срока (TTL = 24 часа), но для данного проекта это приемлемо. В перспективе можно добавить refresh-токены или blacklist.
